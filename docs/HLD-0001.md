## 1. Package layout and module interfaces

```
src/dod/
  __init__.py        __version__ — single source; CLI prints it
  cli.py             M5 — argument parsing, dispatch, exit codes
  workspace.py       M1 — repo root + artifact discovery
  frontmatter.py     M2a — minimal front-matter parser (subset defined in §2.1)
  artifacts.py       M2b — typed Artifact objects + schema validation
  gherkin.py         M2c — wrapper around the official Gherkin parser
  graph.py           M3  — traceability graph build + queries
  checks/            M4  — one module per stage group + registry
    __init__.py        Check registry: (check_id, stage, severity, fn)
    req.py uc.py spec.py design.py code.py collateral.py
  report.py          M6 — text + JSON rendering
tests/               Stage 5 — mirrors src layout; pytest
pyproject.toml       packaging; console script dod = dod.cli:main
```

Module contracts (function signatures are normative for DDs and tests):

| Module | Public interface | Responsibility |
| --- | --- | --- |
| M1 `workspace` | `find_root(start: Path) -> Path`; `discover(root: Path) -> Artifacts` | Locate repo root (nearest ancestor containing `docs/index.md`); collect artifact files by path pattern (`docs/REQ-*.md`, `docs/UC-*.md`, `specs/UC-*.feature`, `docs/HLD-*.md`, `docs/DD-*.md`, `marketing/claims.md`, `src/**`); ignore `.git`, `.venv`, `node_modules`. |
| M2a `frontmatter` | `parse(text: str, path: str) -> FrontMatter` | Parse the §2.1 subset; raise `FrontMatterError(msg, path, line)` — never guess. |
| M2b `artifacts` | `load(fm: FrontMatter, path: str, kind: str) -> Artifact` | Validate required fields per §2.2 table; unknown fields → WARN, missing required → FAIL. |
| M2c `gherkin` | `parse_file(path: str) -> list[Scenario]` | Thin wrapper over `gherkin-official`; converts parser errors to `SpecParseError(msg, path, line)`. |
| M3 `graph` | `build(arts: Artifacts) -> Graph`; `Graph.queries`: `forward_orphans()`, `backward_orphans()`, `coverage(req_id)`, `path_between(a, b)` | Edges per ARCH §4.1 (9 substrate edges + 2 collateral edges from HLD-0002); regex extraction per §3.2. |
| M4 `checks` | `run_all(arts, graph, stage: str | None) -> list[Finding]` | Each check: pure fn `(Artifacts, Graph) -> Iterable[Finding]`; registered with stable id. |
| M5 `cli` | `main(argv) -> int` | §4 commands and exit codes only. |
| M6 `report` | `render_text(findings) -> str`; `render_json(findings) -> str` | Findings sorted by (stage, check_id, path, line) — deterministic output. |

`Finding` (the one shared data type): `check_id: str`, `severity: FAIL | WARN`,
`path: str | None`, `line: int | None`, `message: str`, `fix_hint: str`.
`fix_hint` is mandatory: every failure names the artifact to edit (AGENTS.md §9 —
actionable, no fog).

## 2. Artifact schemas (exact front-matter)

### 2.1 Front-matter subset (parsed by M2a, no YAML library)

A file has front-matter iff line 1 is exactly `---`. It ends at the next line that is
exactly `---`. Inside: `key: value` pairs, keys matching `[a-z][a-z0-9-]*`.
Values: plain scalar (trimmed), double/single-quoted scalar, inline list
`[a, b, c]`, or block list (following lines `- item`). No nesting, no anchors, no
multi-line scalars. Anything else is a `FrontMatterError` with line number.

**Why in-house instead of PyYAML (rejected alternative):** the schema below is ours and
tiny; a full YAML parser drags a dependency plus its implicit-typing traps
(`version: 1.0` becoming a float). This does not contradict §7's Gherkin decision: the
Gherkin grammar has an external authority (Cucumber) we must not diverge from; this
subset has none.

### 2.2 Required fields per artifact type

| Type | Required | Optional | Rules |
| --- | --- | --- | --- |
| `REQ-xxxx.md` | `id` (`REQ-\d{4}`), `title`, `status`, `priority` (`must\|should\|could`) | `owner`, `date` | Body must contain the §4.2 ARCH sections (problem, JTBD, …) — checked by `req.structure`. |
| `UC-xxxx.md` | `id` (`UC-\d{4}`), `req`, `status`, `priority` | `personas` (list) | `req` must match `REQ-\d{4}` and resolve to an existing REQ. |
| `UC-xxxx.feature` | — (Gherkin has no front-matter) | — | Feature header comment `# REQ: REQ-xxxx` optional; each scenario tagged `@REQ-xxxx` (required) and `@UC-xxxx` (optional); tags checked by `spec.tags`. |
| `HLD-xxxx.md` | `id` (`HLD-\d{4}`), `req`, `arch`, `status` | `author`, `date` | Must contain non-empty `## Interfaces`-equivalent (§5 sections) and `## Error handling`. |
| `DD-xxxx.md` | `id` (`DD-\d{4}`), `hld`, `status` | `module`, `date` | `hld` must match `HLD-\d{4}` and resolve; exactly one `hld` value (ARCH §4.1 single-parent). |
| `marketing/claims.md` | — | — | Schema is HLD-0002's; here only its existence is known to M1. |

**Legacy header form:** artifacts approved before this schema (REQ-0001/0002,
ARCH-0001.md) use a bold `**ID:**` block instead of front-matter. M2b accepts it for
`REQ` and `ARCH` kinds, emitting `dod.schema.legacy WARN` ("add front-matter; content
unchanged"). Migration is a Stage 8 docs task, not a semantic edit to approved text.

## 3. Trace graph (M3)

### 3.1 Nodes and edges

Nodes: every discovered artifact, keyed by ID (filename stem; features key on their
`# REQ:` comment or first `@REQ-` tag). Edges are exactly ARCH §4.1:

| # | Edge | Extracted from |
| --- | --- | --- |
| 1 | REQ → UC | `req:` field in UC front-matter |
| 2 | UC → spec | filename pairing `docs/UC-0001.md` ↔ `specs/UC-0001.feature` |
| 3 | spec → REQ | `@REQ-xxxx` scenario tags |
| 4 | REQ → HLD | `req:` field in HLD front-matter |
| 5 | HLD → DD | `hld:` field in DD front-matter |
| 6 | DD → test | `# Trace: DD-xxxx §N` in test files |
| 7 | DD → code | `// Trace: DD-xxxx §N` (or `#`/`<!--`) in source files |
| 8 | code → test | test file imports/instantiates module under test (heuristic: same stem under `tests/`) — WARN-only edge |
| 9 | docs → all | changelog entries cite IDs (`[REQ-0001]` style) |
| 10–11 | collateral edges | HLD-0002 (`claim → feature`, `feature → integration`) |

### 3.2 Extraction rules

- Trace comments: regex `(?://|#|<!--)\s*Trace:\s*(DD-\d{4}(?:\s*§\s*\d+(?:[-,]\d+)*)?)`
  — first match per file is authoritative; later matches are additional edges.
- Edge 8 heuristic stays WARN-only forever (ARCH §4.1 marks it heuristic); it can never
  fail a gate.
- All extraction is line-based (no source parsing): language-agnostic by design
  (REQ-0001 §4). A file with no extractable IDs is a node with no edges, not an error.

### 3.3 Queries (used by checks and `dod trace`)

- `forward_orphans(kind)`: nodes missing a required parent edge (e.g. a DD with no
  resolvable `hld:`) — FAIL direction.
- `backward_orphans(kind)`: nodes no child references (e.g. a DD no test cites) —
  WARN direction (ARCH §4.3: reverse detection informs, forward blocks).
- `coverage(req_id)`: the full reachable set from a REQ; `dod trace --require REQ-0001`
  prints it as an indented tree, exit 0 only if the chain REQ→…→code resolves.

## 4. CLI surface (M5) — commands and exit codes

| Command | Behavior | Exit codes |
| --- | --- | --- |
| `dod check [stage]` (`all` default) | Run M4 groups: `req`, `uc`, `spec`, `design`, `code`, `collateral`, or `all`. Text report to stdout. | 0 no FAILs (WARNs allowed, shown); 1 ≥1 FAIL; 2 usage/env error |
| `dod check all --json` | Same run, JSON on stdout (findings array + summary). | as above |
| `dod trace [--require REQ-xxxx] [--json]` | Print graph; with `--require`, only that REQ's subtree. | 0 subtree resolves; 1 orphan/missing; 2 env |
| `dod init` | Scaffold `docs/index.md`, `specs/`, `marketing/claims.md` template. Never overwrites (existing file → exit 2). | 0 created; 2 refused |
| `dod pack <file>` | Audit one collateral pack (HLD-0002 §5). | 0 deliverable, 1 refuse, 2 bad path |
| `dod version` | Print `__version__`. | 0 |

No other commands. Exit code 3+ reserved (never used). Flags outside this table are
usage errors (exit 2). `dod check` on a non-workspace (no `docs/index.md` upward search)
is exit 2 with a hint to run `dod init`.

## 5. Gate check inventory (M4)

Severity: F = FAIL (blocks), W = WARN. "Stage" is the AGENTS.md §5 stage the check serves.

| check_id | Stage | Sev | What it verifies |
| --- | --- | --- | --- |
| `dod.req.structure` | 0 | F | REQ body has problem, JTBD, value-proposition sections (ARCH §4.2); non-empty. |
| `dod.req.status` | 0 | W | `status` field present and one of draft/approved/deprecated. |
| `dod.uc.trace` | 2 | F | Every UC's `req:` resolves to an existing REQ. |
| `dod.uc.coverage` | 2 | F | Every approved REQ is referenced by ≥1 UC (ARCH §5 Stage 2 gate). |
| `dod.spec.parse` | 3 | F | Every `specs/*.feature` parses with the official Gherkin parser. |
| `dod.spec.tags` | 3 | F | Every scenario has ≥1 `@REQ-xxxx` tag and every tag resolves to an existing REQ. |
| `dod.spec.coverage` | 3 | F | Every approved REQ is tagged in ≥1 scenario. |
| `dod.design.hld-per-req` | 4 | F | Every approved REQ has ≥1 HLD citing it (edge 4). |
| `dod.design.dd-per-hld` | 4 | F | Every HLD has ≥1 DD (edge 5). |
| `dod.design.sections` | 4 | F | HLD/DD contain non-empty interfaces and error-handling sections. |
| `dod.code.trace` | 6 | F | Source files under `src/` (excluding `__init__.py`) contain ≥1 `// Trace: DD-xxxx §N` and each cited DD resolves. |
| `dod.code.orphans` | 6 | W | DDs with no code citing them (reverse detection). |
| `dod.test.trace` | 5 | F | Test files cite a resolvable DD (edge 6). |
| `dod.test.orphan` | 5 | W | DDs with no test citing them. |
| `dod.docs.resolve` | 8 | W | IDs cited in changelog/README resolve to artifacts. |
| `dod.schema.legacy` | — | W | Legacy bold-header artifacts (see §2.2). |
| `dod.collateral.*` | 7 | — | HLD-0002's group; registered here, specified there. |

Registry rule: check ids are stable public surface — renaming one is a breaking change
(semver major). `dod check <stage>` runs exactly the rows with that stage; `all` runs
everything.

## 6. Role manifest (`dod:` extension) — format the checker validates

Roles are standard Agent Skills (`SKILL.md` + agentskills.io front-matter: `name`,
`description`). The `dod:` extension block adds, exactly:

```yaml
dod:
  stage: 3                    # AGENTS.md §5 stage this role serves
  may_touch: ["docs/UC-*", "specs/*"]   # whitelist globs (ARCH §6)
  forbidden: ["src/**", "tests/**"]     # belt-and-braces statement
  produces: ["specs/UC-*.feature"]
```

No other `dod:` keys (unknown key → WARN `dod.role.schema`). Enforcement is harness-side
(permission config generated from `may_touch`); `dod` itself only validates the format.
Adapter files (`AGENTS.md` snippets per harness) are plain docs — no schema.

## 7. Dependencies (resolves ARCH §11 open Q2)

| Dependency | Where | Why acceptable |
| --- | --- | --- |
| `gherkin-official` (pure Python, Apache-2.0, no transitive deps) | M2c only | The spec parser is the one component where diverging from the Cucumber authority would silently mis-validate contracts. "No invented parsers" beats "zero deps". |
| `pytest` | dev/tests only | Not shipped. |

Everything else stdlib. Rejected: (a) vendored minimal Gherkin parser — we would own
divergence risk against Cucumber for a grammar we don't control; (b) cucumber-jvm via
subprocess — JVM dependency, violates "no heavy dependencies" (REQ-0001 §4). If
`gherkin-official` is missing at runtime, `dod check spec` exits 2 with an install hint
— never skips silently (AGENTS.md §8.4: verification is executed, not asserted).
ARCH §11 open Q2 is hereby resolved; record in ARCH v3 amendment.

## 8. Data flow

```
 files on disk
   │ M1 discover (path patterns)            ┌──────────────┐
   ▼                                        │ M4 checks    │
 Artifacts: {kind, path, text}              │  registry    │
   │ M2a parse → M2b validate               │  fn per id   │
   ▼            ── errors become            ▼
 typed Artifact + load errors ────────► Findings ──► M6 report ──► stdout
   │ M3 build (regex extraction)           ▲            └─► --json
   ▼                                        │
 Graph (nodes, 11 edge types) ──────────────┘
```

`dod check all` sequence: discover → parse/validate (load errors become Findings, run
continues) → build graph from what loaded → run check groups in registry order → render.
One bad file degrades to its own Findings; nothing aborts the run (error handling §9.2).
No writes, no network, no env reads beyond argv and cwd — the whole tool is a pure
function of repo state (ARCH §5; REQ-0001 §4.3).

## 9. Error handling

### 9.1 Categories and exit mapping

| Category | Example | Behavior | Exit |
| --- | --- | --- | --- |
| Usage error | unknown flag, bad stage name | argparse message, no run | 2 |
| Environment error | not a workspace, `gherkin-official` missing, unreadable dir | message + fix hint, no partial report | 2 |
| Artifact defect | bad front-matter, unparseable feature, missing section, orphan edge | becomes Finding(s) with path:line + fix_hint; run continues | 1 (if any FAIL) |
| Internal error (bug) | unexpected exception | print crash note (§9.3) + partial findings; never exit 0 | 1 |

### 9.2 Rules

1. **Never crash on input:** every file-level parse error is caught at the M2 boundary
   and converted to a Finding; a file that fails to parse contributes no nodes/edges.
2. **Never silently skip:** a skipped check (missing dep, unreadable path) emits a WARN
   naming what was skipped.
3. **Line numbers:** Findings carry the offending line when the parser knows it
   (front-matter, Gherkin, regex scans); otherwise file-level only.
4. **Encoding:** files read as UTF-8; decode error → FAIL `dod.schema.encoding` with the
   byte offset.
5. **Determinism:** findings sorted by (stage, check_id, path, line); dict iteration
   order never leaks into output; no timestamps in reports.

### 9.3 Message content standard (normative)

Every message the tool shows a human — Findings of any severity, CLI errors,
degraded-mode warnings — MUST convey three parts, in this order:

1. **What happened** — a plain sentence naming the problem and its kind
   (ERROR/WARN). Never a bare code, a stack trace, or a raw exception repr.
2. **Where and why** — the precise location and cause: `path:line` (or entry
   index) plus the rule id and the offending content (the value, key, id, or
   line that triggered it), so the human never has to hunt for the problem.
3. **What to do next** — a concrete action valid right now: the exact edit to
   make, the command to run, or where to look. If no fix can be named, the
   message MUST still name an escalation path ("file a bug at <url> with this
   message").

Rules:
- Check ids (FM001, COV002, …) supplement the sentence, never replace it.
- `{exc!r}`-style internals may appear only as an appended detail after
  parts 1–3, never as the message itself.
- Crash notes follow the same standard: what happened (a check crashed — a tool
  bug, not the user's workspace), where (check id, workspace path), and the next
  step (file a bug at the project tracker with this output; the rest of the
  report was still written).
- Degraded-mode warnings (DD-0001 §6) follow the same standard: what is missing,
  what is being skipped instead, and the exact install/pin command.

This standard is reviewable: a message missing a part is a defect like any other.

where a machine enforces it. "no gate" is recorded honestly: those rows are held by
