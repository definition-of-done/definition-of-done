## 1. What we are building, in one paragraph

Definition of Done is a **repo-local engineering substrate**: a set of artifact schemas, a
deterministic gate runner, roles shipped as standard Agent Skills, and thin harness adapters.
It installs into a project as a CLI (`dod`) plus files in the repo. It never talks to a model
itself. The user's own harness — Claude Code, OpenCode, a homegrown local stack — reads the
artifacts and skills and runs the agents. We own the contracts and the gates; the harness
owns execution.

It serves the full spectrum — from the vibiest of vibe coders to the most traditional
old-school engineer. Keep prompting the prototype into existence; the substrate turns it
into software someone else can inherit.

**We do not build:** a model, an agent loop, a harness, an IDE, a hosted service, telemetry.
(REQ-0001 §6; constraint §4.3: "artifacts and gates are the product; agent runtimes are pluggable.")

## 2. System context

```
 user's repo ─────────────────────────────────────────────────┐
 │  docs/ specs/ tests/ src/          ← the user's project   │
 │  .dod/  ← installed: schemas, roles, gates config         │
 └───────────────▲───────────────────────────────▲───────────┘
                 │ read/write artifacts          │ role manifests, prompts
        ┌────────┴────────┐            ┌─────────┴──────────┐
        │  dod CLI (us)   │            │  user's harness    │
        │  validate, trace│            │  Claude Code,      │
        │  gate, scaffold │            │  OpenCode, custom  │
        └─────────────────┘            └────────────────────┘
```

The CLI and the harness never call each other. They meet only through **files in the repo**.
This is the decoupling that makes us harness-agnostic: any tool that can read a Markdown file
and respect a write-scope list is a valid harness.

## 3. Layers and modules

Four layers, dependencies point downward only. One module, one concern (AGENTS.md §3.6).

| Layer | Module | Concern (single sentence) | May import |
| --- | --- | --- | --- |
| L0 substrate | `artifacts` | Define and validate artifact schemas (REQ, UC, feature, HLD, DD, review, ADR) and their IDs. | stdlib |
| L1 verify | `trace` | Build the `REQ → UC → spec → test → code → docs` graph from artifact IDs and `// Trace:` markers; report breaks. | `artifacts` |
| L1 verify | `gates` | Run stage exit gates as pure functions: repo state in, verdict + reasons out. | `artifacts`, `trace` |
| L2 orchestrate | `roles` | Ship each role as a standard Agent Skill (`SKILL.md` + YAML front-matter): stage, inputs, write scope, forbidden actions, stop condition. | `artifacts` |
| L3 adapt | `adapters/*` | Install skills into each harness's native layout (subagent files, plugin dirs); generic fallback is AGENTS.md. | `roles` |
| L4 surface | `cli` | `dod new/check/trace/gate/run-stage` commands; human- and CI-readable output. | all above |

**Boundary rules**

- `gates` is pure: no network, no subprocess to any model, no LLM calls. Deterministic
  verification beats probabilistic generation (AGENTS.md §2). A Review Agent's opinion is an
  *artifact* a human reads — never an automatic pass.
- `adapters` are leaves: nothing imports them; users delete the ones they don't use.
- Adapters translate, never add logic. If adapter code grows a decision, that decision belongs
  in `roles` or `gates`.
- The artifact files themselves are the API between us and the world. Schema changes follow
  semver; a v1 repo must stay readable by v2 tooling.

## 4. The artifact substrate (L0)

Artifacts are plain Markdown with a YAML front-matter block — human-auditable in any editor,
machine-parseable without a Markdown AST dependency.

| Artifact | Path | Key fields | Written by |
| --- | --- | --- | --- |
| Requirement | `docs/REQ-xxxx.md` | id, status, jtbd, value, non_goals | Product Analyst |
| Architecture | `docs/ARCH-0001.md` | id, status, boundaries, deps | Architect |
| Use case | `docs/UC-xxxx.md` | id, req (parent), scenarios | Spec Writer |
| Behavior contract | `specs/UC-xxxx.feature` | Gherkin, 1:1 with UC | Spec Writer |
| Design | `docs/HLD-xxxx.md`, `docs/DD-xxxx.md` | id, parent (HLD → one REQ; DD → exactly one HLD), interfaces | Architect |
| Review notes | `docs/review/UC-xxxx.md` | id, verdict, refactor_orders | Review Agent |
| ADR | `docs/adr/NNNN-*.md` | decision, reason, rejected | Docs Agent |
| Collateral | `docs/collateral/*.md` | id, tags (req/uc/feature), evidence link, verified flag | All roles (capture); Compiler (packs) |

Trace markers: every public code unit carries `// Trace: DD-xxxx §N` (language-appropriate
comment) — the design document is the direct parent of code. Tests additionally cite the UC
scenario they exercise. `docs/index.md` is the generated traceability table — generated by
`dod trace`, never hand-edited, so it cannot drift.

### 4.1 Traceability graph

`dod trace` builds one directed graph from artifact front-matter and Trace markers — files
only, no database or graph store. Forward edges prove coverage; reverse checks detect orphans.

| Edge | Link source | Reverse (orphan) check |
| --- | --- | --- |
| REQ → UC | UC front-matter `req:` | UC without a REQ fails Stage 2 |
| REQ → HLD | HLD front-matter `req:` | HLD without a REQ fails Stage 1 |
| HLD → DD | DD front-matter `hld:` (exactly one parent) | orphan DD and zero-DD HLD fail Stage 4 |
| UC → spec | `specs/UC-xxxx.feature` + front-matter | spec without a UC fails Stage 3 |
| spec → test | test cites UC scenario ID | scenario with no test fails Stage 5 |
| DD → code | `// Trace: DD-xxxx §N` | code without a Trace marker fails Stage 6 |
| DD → test | test cites DD component | test with no DD component fails Stage 5 |
| REQ → collateral | collateral tag `req:` | zero-collateral feature flagged at integration (REQ-0002) |
| UC → docs | changelog/README cite UC IDs | shipped UC with no doc mention fails Stage 8 |

## 5. Gate model (L1)

Each pipeline stage maps to one gate module: `gate_stage0(req) -> Verdict`, and so on.
`Verdict = pass | fail(reasons[])`. CI runs `dod gate --stage N --diff` on every PR; the
verdict is mechanical, the signoff is human (AGENTS.md §5: an agent never signs its own work).

| Stage | Gate checks (deterministic) |
| --- | --- |
| 0 | REQ has problem, JTBD, value, launch message; exit checklist all checked |
| 1 | ARCHITECTURE exists; new component listed in a boundary; every dependency has a rationale line |
| 2 | Every UC cites a REQ; every REQ covered by ≥1 UC; no orphan IDs |
| 3 | Feature files parse; each UC has happy + edge + failure scenarios |
| 4 | Every REQ has an HLD; every HLD has ≥1 DD (DD has exactly one HLD); interfaces and error handling sections non-empty |
| 5 | Tests compile and fail (pre-implementation) or pass (post); every test cites a UC scenario and a DD component |
| 6 | Suite green; lint/type clean; zero skipped/xfail; no public code unit without a `DD-xxxx §N` Trace marker |
| 7 | Review notes exist and predate merge; clean-code checklist present |
| 8 | Changelog/README/ADR updated in same diff; `dod trace` fully resolves |

## 6. Roles and adapters (L2–L3)

Roles are **standard Agent Skills** (SKILL.md format, agentskills.io — the open,
vendor-backed standard), not a bespoke manifest format. One skill per role; the discipline
of AGENTS.md §6 lives in YAML front-matter plus a short body:

```markdown
---
name: implementer
description: Implement one module from its approved DD, inside the task's write scope.
dod: { stage: 6, inputs: [specs/UC-*.feature, docs/DD-*.md, tests/],
       write: ["src/<module>/**"], forbid: [tests/**, specs/**],
       stop: stage_boundary }
---
Read the DD sections in your inputs. Write only inside `write`. Record collateral as you
work (§7). Stop at the stage boundary and hand back; never run on.
```

Why skills, not custom manifests: one manifest, many harnesses — the ecosystem (Copilot,
Codex, Gemini CLI, VS Code, Cursor) already reads this format; a custom schema would rot
into per-harness translation drift. The `dod:` front-matter block is the extension point:
harnesses ignore it, `dod` enforces it. **AGENTS.md stays the primary harness interface** —
every harness reads it; skills are what it points to.

First-party adapters: **Claude Code** (subagents), **OpenCode** (config), **generic**
(AGENTS.md pointing at the skills directory — works anywhere). Adapter contract: install
the skills and enforce their write scope. No intelligence, no gates. MCP is a possible
future **read-only** adapter (exposing `dod trace`/`gate` as tools); it is not a dependency
and never a write path.

## 7. Collateral capture (REQ-0002)

**Claims carry receipts.** Every role records value signals — selling points, pros/cons,
caveats, competitive notes, demo moments — as a side effect of normal work, never as a
separate marketing task.

- **Shape:** append-only entries in `docs/collateral/`, one file per feature, YAML
  front-matter per entry: `tags` (REQ/UC/feature IDs), `claim`, `evidence` (artifact path,
  test run, benchmark), `verified | unverified`. A claim without an evidence link is
  recorded but marked `unverified` — never silently dropped, never silently trusted.
- **Graph:** entries join the traceability graph as REQ → collateral edges (§4.1);
  `dod trace` flags a feature reaching integration with zero entries (REQ-0002 FR-4).
- **Compilation:** a Compiler role generates audience-targeted packs (developer-facing,
  executive-facing) per feature and per release. The compiler is a role, not a gate: it
  produces an artifact a human reads. Gates stay pure (§3 boundary rule).
- **Consumption:** the marketing bot consumes compiled packs only — the pack is where
  every claim resolves to evidence or an explicit `unverified` mark.

## 8. Technology decisions

| Decision | Choice | Reason | Rejected |
| --- | --- | --- | --- |
| Language | Python 3.12+, stdlib-first — **required only for the `dod` gate runner** | deterministic CLI, Gherkin tooling exists, contributor pool matches audience | Go (slower community iteration), Node (audience skews Python; npm shim for install) |
| Runtime split | Everything else runs on the user's runtime: roles execute as SKILL.md skills in the user's harness; the gate runner shells out to the project's own test toolchain | the user's stack stays theirs; we own contracts and verification, not execution | requiring Python of every user (excludes JS/Rust shops from the substrate) |
| Role format | Agent Skills standard (SKILL.md, agentskills.io) | open standard, already read by major harnesses; one manifest, many harnesses | custom YAML manifests (per-harness translation drift) |
| Artifact format | Markdown + YAML front-matter | human-auditable anywhere (AGENTS.md §7), parseable without heavy deps | JSON/YAML bodies (unreadable to humans), pure prose (unparseable) |
| Distribution | PyPI package; npm wrapper later | both audiences, zero-cost install paths | hosted service (REQ-0001 §6) |
| Core dependencies | **none** beyond stdlib | supply-chain trust for a tool that gates merges | `parse-gherkin` etc. — a vendored minimal Gherkin parser is a Stage 4 design question, decided with a rationale line, not silently |
| State | files in repo, no database | the repo *is* the product's database; auditable by git | SQLite sidecar (hidden state, drift) |

## 9. Relationship to adjacent tools

- **Spec Kit and similar spec-driven frameworks**: they make specs true
  before code; we keep specs true *while code churns*. The missing piece
  they leave is the enforcement layer — machine-checked traceability,
  drift gates, and an audit trail that accumulates as the project ages.
  The primitives are compatible: a Spec Kit spec is an input to our
  pipeline, and `dod init` importing one is a plausible later feature.
- **MCP servers**: an adapter surface, not the product. If an MCP server
  ever exposes our artifacts read-only to MCP-capable clients, it is a
  thin layer over the files, never a second source of truth (§6).
- **CI systems**: we are the checks CI runs, not a CI system.

## 10. Dogfooding rule

This repository runs its own pipeline: REQ-0001 → this file → UCs → specs → code. The first
real user of `dod` is the `dod` repo, and every gate we ship must have caught (or would have
caught) a real slip we made here. If a gate never fires in dogfooding, it is suspect.
