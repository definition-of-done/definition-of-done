# HLD-0002 — Collateral subsystem: capture, evidence, coverage, packs

**Traces to:** REQ-0002 (FR-1…4, AC-1…3; coverage map in §10), UC-0004 (capture),
UC-0005 (compilation), UC-0005 (compilation),
ARCH-0001.md §7. Builds on HLD-0001: reuses M1 discovery, M2a front-matter subset,
M3 graph, M4 registry, M5 CLI. This HLD also answers REQ-0002 §7's three open questions
(§2.1, §5, §6).

**Scope:** the collateral *data formats* (entries, packs) and the *deterministic checks*
over them (schema, evidence resolution, coverage, pack audit). The Compiler itself is a
role (Agent Skill), not code — ARCH §7: "the compiler is a role, not a gate." What ships
as code is everything a role's output must satisfy, plus `dod pack`, the mechanical
half of the compiler's self-check.

**Design constraints (inherited):** same as HLD-0001 — pure, deterministic, no network,
no LLM calls; capture must stay a side effect of normal work (REQ-0002 FR-1), so nothing
here may make recording an entry expensive or require a second tool.

## 2. Collateral entry format (M1 discovers `docs/collateral/*.md`)

### 2.1 File and entry shape

File: `docs/collateral/<feature-slug>.md` — one file per feature (slug = kebab-case
feature name, e.g. `trace-graph.md`). Optional file front-matter: `feature` (human
name), `uc` (optional `UC-\d{4}`). Body = entries:

```
+++
id: COL-0007
kind: selling-point
claim: Gate checks run fully offline — no data leaves the machine.
tags: [REQ-0001, UC-0003]
evidence: docs/ARCH-0001.md#5-gates
verified: true
date: 2026-11-07
+++
```

`+++` delimits entries (a file-level `---` front-matter would collide with HLD-0001
§2.1's parser, which treats a leading `---` as *the* front-matter block). Entry fields
use exactly the HLD-0001 §2.1 subset grammar, parsed by a reused `parse_block()` — one
grammar, two framings (`---` file header, `+++` entry).

### 2.2 Entry schema

| Field | Required | Rule |
| --- | --- | --- |
| `id` | yes | `COL-\d{4}`, unique across all collateral files |
| `kind` | yes | one of `selling-point`, `pro`, `con`, `caveat`, `competitive`, `demo` |
| `claim` | yes | one sentence, quoted scalar allowed; no marketing fog (AGENTS.md §9) |
| `tags` | yes | inline list; ≥1 entry matching `REQ-\d{4}`; UC/feature IDs optional extras |
| `evidence` | no | repo-relative path, optionally `#anchor`; a test run or benchmark is recorded as the path to its committed report/log |
| `verified` | no | `true` \| `false`, default `false` |
| `date` | no | ISO date |

Consistency rule (the honesty rule, FR-2): `verified: true` requires `evidence` present
**and** resolving (§4). `evidence` without `verified: true` is legal (recorded, not yet
checked). A claim with neither is legal and renders as unverified. Nothing is ever
silently dropped or silently trusted.

**Append-only** is a role duty (every role skill carries it): entries are added, never
edited or deleted; corrections are new entries superseding old via `supersedes: COL-xxxx`
(optional field). `dod` does not police history — it has no git access (HLD-0001 §8
purity); review agents enforce append-only on diffs.

## 3. Graph integration (M3)

The two edge types HLD-0001 §3.1 reserves for this HLD:

| Edge | Extracted from | Direction semantics |
| --- | --- | --- |
| REQ → collateral entry | `tags:` list, `REQ-\d{4}` members | coverage: which REQs have captured value signals |
| entry → evidence | `evidence:` path | resolution: does the receipt exist |

Unresolvable `tags` REQ ids are forward-orphans (FAIL); a second REQ tag on one entry is
legal (one observation can serve two requirements).

## 4. Checks (registered in M4, run by `dod check collateral`)

| check_id | Sev | What it verifies | Serves |
| --- | --- | --- | --- |
| `dod.collateral.schema` | F | Entry parses; required fields present; `kind` in enum; `id` unique; `verified: true` implies `evidence` present | FR-2, AC-1 |
| `dod.collateral.evidence` | W | `evidence:` path exists in repo (anchor not deep-checked); broken → name entry + stale path | AC-2 (UC-0005 S3) |
| `dod.collateral.coverage` | W | Every REQ that has code citing a DD that traces to it (i.e. REQ is "integrated") has ≥1 collateral entry; zero entries → flag naming the REQ | FR-4, AC-3 (UC-0004 S4) |
| `dod.collateral.tag-resolve` | F | Every `REQ-\d{4}` in `tags:` resolves to an existing REQ | trace integrity |

Coverage severity is WARN, not FAIL: REQ-0002 says "flagged," and a silent feature must
not block a merge — it is a debt signal a human triages (ARCH §4.3: reverse detection
informs). "Integrated" is defined mechanically as: REQ reachable from ≥1 source file via
REQ→HLD→DD→code edges (HLD-0001 §3.1 edges 4, 5, 7).

## 5. Pack format (`marketing/packs/*.md`) and `dod pack`

A pack is the compiler role's output artifact: per-release
(`marketing/packs/release-<tag>.md`) and per-feature (`marketing/packs/<feature-slug>.md`).

Structure (normative): H1 title; then audience sections `## Developer` and
`## Executive`; each claim is a list item:

```
- Gate checks run fully offline — no data leaves the machine.
  <!-- Collateral: COL-0007; Evidence: docs/ARCH-0001.md#5-gates -->
```

Rules: every claim item carries a `<!-- Collateral: COL-xxxx; Evidence: ... -->`
comment, or the literal suffix `[unverified]`. Audience selection is mechanical:
Executive section = entries of kind `selling-point | pro | demo`; Developer section =
all kinds; `caveat` and `con` entries must appear in whichever section cites their
subject claim (no burying the cons).

`dod pack <file>` (new M5 command, registered in HLD-0001 §4) is the pack audit —
UC-0005 S4's self-check, made deterministic:

| Verdict | Condition | Exit |
| --- | --- | --- |
| pass | every claim cites a resolvable `COL-xxxx` whose evidence resolves, or is marked `[unverified]` | 0 |
| refuse | any claim lacks both, cites a nonexistent entry, or an evidence link is stale | 1, naming each offending claim line and the source entry to fix |

`dod pack` on a nonexistent/unparseable pack → exit 2 (usage/env, HLD-0001 §9.1).
The compiler role runs `dod pack` on its own output before delivering; CI runs it on
every pack in `marketing/packs/`. The role does the judgment (phrasing, ordering,
emphasis); the CLI does the audit. Neither trusts the other.

## 6. Roles (format per HLD-0001 §6)

- **Every existing role** gains one collateral duty line in its SKILL.md: *while
  producing your stage artifact, append any value signal to `docs/collateral/` per §2.*
  Their `may_touch` gains `docs/collateral/*`. This is FR-1's mechanism — capture is
  instruction-shaped, not tool-shaped, so it works in every harness.
- **Compiler** (new role): `stage: 7`, `may_touch: ["marketing/packs/*"]`, forbidden:
  everything else. Reads `docs/collateral/`, writes packs, runs `dod pack`, delivers
  only on exit 0. Produces artifacts a human reads; blocks nothing.

## 7. Data flow

```
 role work ──(skill duty)──► docs/collateral/<feature>.md   [append entries]
                                   │ M1 discover → parse_block per entry
                                   ▼
                    entries ──► M3 graph (edges §3) ──► M4 collateral checks ─► findings
                                   │
 Compiler role ◄───────────────────┘  (reads entries + repo)
     │ writes marketing/packs/*.md
     ▼
 dod pack <pack> ──audit──► exit 0 deliver │ exit 1 refuse + name claims
     │
 CI: dod check collateral (schema, evidence, coverage) on every run
```

## 8. Error handling

1. A malformed entry yields a FAIL naming file + entry index; parsing continues with the
   next `+++` block (one bad entry never hides the rest of the file).
2. A collateral file with zero parseable entries → WARN `dod.collateral.empty` (likely a
   delimiter mistake), not silence.
3. Missing `docs/collateral/` directory is not an error; coverage then flags every
   integrated REQ (absence of evidence is a finding, not a crash).
4. `dod pack` never rewrites the pack; it only reports. Fixing is the compiler role's
   or a human's job — the auditor does not edit the audited (AGENTS.md §6: no agent
   approves its own work).
5. Determinism: entries processed in (file, index) order; findings inherit HLD-0001
   §9.2 sorting.
