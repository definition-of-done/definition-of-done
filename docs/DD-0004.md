# DD-0004 — CLI and report rendering (M5, M6)

**Traces to:** HLD-0001 §4 (commands, exit codes), §8 (errors), §9 (data flow).
Modules: `dod/cli.py`, `dod/report.py`, `dod/init.py`. This DD is the only place
`sys.exit` is called; everything below it raises or returns.

## §1 Command dispatch

```python
def main(argv: list[str]) -> int:
    """argparse tree mirroring HLD-0001 §4 exactly. Returns the exit code;
    `if __name__ == "__main__": sys.exit(main(sys.argv[1:]))`."""
```

Global behavior: workspace discovery happens once per command (HLD-0001 §9);
`--cwd` overrides the start directory (tests and CI runners use it). Subcommand
handlers are plain functions `cmd_check(args, ws) -> int` — injectable, no
argparse types past this layer. `dod pack` dispatches to DD-0006's
`audit_pack(ws, path) -> int`; `dod trace` to DD-0002 §3.

Exit-code discipline: handlers return 0/1/2 only. Uncaught exceptions reaching
`main` are bugs: print `dod: internal error: {exc}` plus a one-line traceback
summary, exit 2. (Exit 2 = "the tool could not do its job", which is honest here.)

## §2 `dod check` pipeline

```python
def cmd_check(args, ws) -> int:
    graph = TraceGraph(); graph.build(ws, trace_sources=CodeIndex.scan(ws.root))
    ctx = GateContext.build(ws, graph, options_from(args))
    results = run_all(ctx)                 # DD-0003 §1
    if args.fix: apply_fixes(ctx, results) # re-run affected checks after fixes
    emit(results, fmt=args.format)
    return 1 if any(r.findings FAIL) else 0
```

`--fix` re-runs the full suite after applying fixes and reports the post-fix state
(so the user sees what remains), then exits on the post-fix results. Workspace
errors inside `--fix` (unwritable file) become findings, not crashes.

## §3 Report rendering

```python
def render_text(results: list[CheckResult], *, color: bool) -> str:
    """Grouped by check id. Findings: `path:line: SEVERITY [id] message`.
    Footer: `n checks, m findings (k fixable) -> PASS|FAIL`.
    Color: ANSI only when stdout is a TTY and NO_COLOR unset; WARN yellow,
    FAIL red, PASS green. No glyphs (Windows terminals, CI logs)."""

def render_json(results, *, started_ms: int) -> str:
    """SchemaVersion 1: {"version": 1, "ok": bool, "duration_ms": int,
    "checks": [{"id", "stage", "ok", "findings": [...]}]}. Keys sorted,
    LF, no trailing whitespace. This schema is public surface: additive
    changes only; bump version on breaking ones."""
```

Why both a footer line and per-check detail: CI greps the footer (`dod check
--format=json | jq .ok`), humans read the detail. Empty results render the footer
alone — `dod check` on a clean repo prints one line, not a shrug.

## §4 `dod init`

Templates are package data (`dod/templates/*`), not generated strings — they are
user-facing docs and belong in files a human edits. `dod init` does not create a
git repo or touch git config (the harness's job).

## §5 `dod version`, `dod role validate`, `dod index --fix`

Thin handlers: `version` prints `__version__` (single source:
`importlib.metadata.version("definition-of-done")`). `role validate` runs
RL001 (DD-0003 §3) against one path without building the full graph — fast for
CI on role-only PRs. `index` = `sync_index` (DD-0002 §2); prints changed/unchanged.

## §6 Error handling

| Condition | Behavior |
| --- | --- |
| Workspace not found | `dod: no workspace found (looked for docs/index.md from ... up). Run 'dod init' to start one.` → exit 2 |
| Unknown subcommand | argparse default, exit 2 |
| `--format=json` requested on a command without json | argparse error, exit 2 |
| stdout closed (`dod check \| head`) | catch BrokenPipeError, exit 0 quietly (standard CLI courtesy) — no message, none wanted |
| `--stage` without `check` | argparse error, exit 2 |

All messages follow the 3-bit standard (HLD-0001 §9.3): the workspace-not-found
message already carries problem → where it looked → next step (`dod init`).
argparse's built-in errors (unknown subcommand, bad flag) are accepted as
compliant: they name the invalid input and print the usage line, which is the
next step. No raw tracebacks from this module; unexpected exceptions are
handled by the top-level crash path (DD-0003 §1, exit 70).
