# STD-0001 — Coding standards

**Scope:** every line under `src/dod/**` and `tests/**`. Applies from the first Stage 5
commit. **Precedence:** AGENTS.md > approved ARCH/HLD/DD > this document > general
convention. If a DD contradicts a rule here, the DD wins for that module — and this
document gets amended, not silently ignored. A rule violation found in review is a
defect like any other; if a rule is wrong, fix the rule in writing, not by exception.

## 1. Stack (inherited, not renegotiated)

- Python 3.12+, stdlib-first. The only dependencies are the ones HLD-0001 §7 approved:
  `gherkin-official` (M2c only) and `pytest` (dev/tests only). A new dependency needs an
  HLD amendment first — never a PR that quietly adds one.
- No framework, no build system beyond `pyproject.toml`, no code generation.

## 2. Formatting and types

- PEP 8, 4-space indent, max line length 100.
- Type hints on every public function and class — the HLD §1 interface signatures are
  normative; copy them exactly. Use builtin generics (`list[str]`, `X | None`).
- Private by default: anything not in the module's declared public interface is
  prefixed `_` or lives below the module's public section.

## 3. Structure

- Module boundaries are HLD-0001 §1. Code lives in the module its DD assigns; moving
  code between modules is an HLD change, not a refactor.
- Imports: absolute, stdlib first. No cycles; dependencies flow downward
  (`cli` → `checks`/`report` → `graph` → `artifacts`/`frontmatter`/`workspace`).
  A lower module never imports a higher one.
- Shared data types (`Finding`, `Artifact`, `FrontMatter`, `Scenario`) are dataclasses
  defined in the module that owns them; frozen where possible. Never pass untyped dicts
  across module boundaries. No mutable module-level state.

## 4. Functions

- One function, one job. If you need "and" to describe it, split it.
- Small enough to read at a glance — roughly 40 lines is a smell threshold, not a law.
- Verbs name functions (`build_graph`), nouns name data (`graph`). No abbreviations a
  newcomer wouldn't know.
- At most 3 parameters; more means the call needs a dataclass.
- No boolean flag arguments that switch a function into different behavior — write two
  functions.
- Early return over nested conditionals; maximum nesting depth 2.

## 5. Errors and messages

- Follow HLD-0001 §9 in full: never crash on input, never silently skip, findings carry
  `path:line` when known, output is deterministic.
- Custom exceptions are defined in the module that raises them, named `*Error`, and
  carry `path`/`line` when the site knows them (like `FrontMatterError`).
- `except Exception` appears only in the CLI crash handler HLD §9.1 defines. Everywhere
  else, catch the specific exception you can handle — or don't catch it.
- Every message a human sees follows HLD-0001 §9.3 (problem / cause with location /
  next action). `fix_hint` is mandatory on every Finding. This document does not restate
  the standard; §9.3 is the single source.

## 6. Comments and docstrings

- Comments say **why**, not what. If code needs a *what* comment, rewrite the code.
- Every public function and class has a one-line docstring; add argument/return notes
  only when not obvious from the signature.
- No commented-out code, no TODO without an issue id, no docstrings that restate the
  signature.

## 7. Tests

- pytest only; `tests/` mirrors `src/dod/` layout (one test module per source module).
- One behavior per test; name it `test_<unit>_<condition>_<outcome>` so the name reads
  as a sentence and the failure output explains itself.
- Deterministic: no network, no wall-clock, no sleeps, no ordering dependencies, no
  skipped tests without a WARN-worthy reason and an issue.
- Spec scenarios are the test source: each `@REQ-xxxx` scenario maps to at least one
  test; the test cites the scenario in a comment.
- Fixtures over factories over setup inheritance. `tmp_path` for filesystem tests —
  never touch the repo working tree.

## 8. Keep it simple (the binding part)

- **YAGNI:** implement what the DD specifies, nothing adjacent. No hooks, plugins,
  config knobs, env vars, or "future-proof" abstractions nobody asked for.
- **Rule of three:** no abstraction until the third concrete use exists. Two similar
  functions are cheaper than a wrong base class.
- Prefer plain functions over classes; a class only for data (dataclass) or when a DD
  declares one. No inheritance hierarchies, metaclasses, or decorator magic.
- No parallel implementations "in case". One way to do it, chosen from the approved
  design.
- If you can't name something simply, the design isn't finished — stop and raise it
  (AGENTS.md: a confident guess is failure), don't improvise intent in code.

## 9. Commits

- Style `<type>: <summary> (REQ-xxxx)`; summary in imperative mood, ≤ 72 chars.
- Every commit compiles and passes the tests it ships with. No drive-by formatting of
  files your change doesn't touch.
